## 二、协作原则（用户原话口径）

1. **参数描述**：所有新增 shader 参数必须带 Inspector 中文悬停描述；所有自定义 UI 控件必须带 `tooltip_text`。
2. **分阶段**：总体工程量大，可分阶段设置阶段性目标。只有阶段内所有验收条件满足、该做的都做完、自审无任何问题，才可进入下一阶段。
3. **机器性能**：本机配置一般、芯片较老、使用核显。使用 run 功能时必须充分考虑本机承受能力，否则可能"炸机"。
4. **不要频繁喊"继续"**：只在**抵达重要分界线**或**出现需要商量的分歧点**时，才给当前对话打终止符；其余时间自己连续推进。
5. **四象限对照**：
   - liltoon 有、我们没有 → **做**，朝完全还原的目标前进；
   - liltoon 有、我们也有 → **自查**，确认是否完全一致，有误差就回到本条；
   - liltoon 没有、我们也没有 → **不做**，不在实现目标内；
   - liltoon 没有、我们恰巧有 → **保留**，但没有继续深入的必要。
6. **A/B/C 处置**：
   - **不做 A 类**（原版没有的能力），因为偏离"做一个 Godot 版 liltoon"的初始目标；
   - **B 类（能做未做）必须把目标设为"完全还原"**。只有在逼近过程中产生了大量难以接受的性能开销或开发代价，才妥协为"原版阉割版"放行，且不再作为待办。**不得以"代码复杂、不方便做"为理由**——可以妥协的只有硬件、软件等客观条件，不包括自己；
   - **完全无法做的**（仅 Unity 内可用、移植后功能天然退化成另一种形态、语言特性导致 GDScript 无法复刻等），放行视为"不做"，从待办移除。
7. **非功能性还原**（缩略图、说明等）除第 1 条提到的编辑器内指引外，**一律推迟到收尾阶段**。
8. **gdmcp 辅助开发**：使用 `.gdmcp/bin/gdmcp.exe`（`localhost:9080`）辅助开发。若出现意外导致 9080 连接断开、或 Godot 编辑器被关闭，**可以先停止工作并汇报**，不必强行继续。
9. **允许把频繁 run 的行为拆开跑**：对于需要频繁 run 的行为，可以把它拆分成多个带间隔的批次执行，并由助手给出**建议的等待时长**，以防止不测（蓝屏、资源累积等）。拆分不视为偷工减料，但必须在汇报里说明拆了几段、每段间隔多少、有没有失败。
10. **不要反复请示下一步**：用户可能不看选项直接回"继续"。除非遇到需要裁定的分歧、或环境硬阻塞（渲染跑不了、编辑器关了），否则按既定计划连续推进；阶段结束做**汇报**即可，汇报不等于请示。

11. **冒烟必须设硬超时**：跑 headless 冒烟一律用 `tools/smoke.ps1`（默认 120 秒超时后强杀），**不要直接调 `godot --headless -s ...`**。

    2026-10-28 踩过：`preset_library.gd` 里 `anisotropy_2_matcap` 键重复 → 依赖脚本编译失败 → `smoke_test.gd` 仍继续执行、调用不存在的 `apply_to_material` → 进程卡住 5 分钟不退出，两次调用各留一个僵尸进程。headless **不创建窗口**，"没看到窗口"本身不是卡住的证据，"长时间不返回"才是。

    超时脚本除了防挂死，还有个副作用是好事：被杀时会打印最后几行输出，编译错误正好在里面。

## 三、补充约定（实战沉淀）

### 参数与描述

1. 描述必须写成**紧邻 `uniform` 正上方的 `/** 中文 */`** 块：写清作用、取值范围/单位、默认行为，不能只翻译参数名。
   - 依赖的 `.gdshaderinc` 必须在某个根 shader 的 `#include` 链里，否则解析不到。
2. **绝对禁止改写 `EditorProperty.tooltip_text`**：该字段是编辑器写入的文档 id（形如 `property|Class|prop`），覆盖成普通文本会触发 `Invalid doc id`，悬停显示全黑空框。描述注入到属性行内部控件的 `tooltip_text`。
3. 新增 uniform 必须同步 `addons/liltoon_gd/editor/preset_library.gd` 的 `BASE`（sampler 除外）。

### 修改与验证

4. **改完必须跑冒烟**，失败先修：
   ```
   godot --headless --path . -s res://tools/smoke_test.gd
   ```
   判读：每个 shader 都要出现"参数描述应完整（缺失 []）"。
5. **渲染编译自检**（一次一个变体）：
   ```powershell
   # 列出全部变体与索引
   powershell -ExecutionPolicy Bypass -File tools\check_all_shaders.ps1 -ListOnly

   # 跑单个变体；`--` 之后才是本工具的参数
   godot --path . res://tools/compile_check.tscn --quit-after 10 --resolution 640x360 -- --index=10
   ```
   判读：出现 `COMPILE_CHECK_DONE` 且 stderr 无 `SHADER ERROR`。
   **不要背靠背连续跑**：用 `tools\check_all_shaders.ps1` 逐进程执行，**建议间隔 30–60 秒，连续 5–10 次后让机器静默几分钟**再继续（见原则第 9 条与 `ROADMAP.md` 的 RISKS）。中断后用日志里的 `START` 行定位到第几个。
6. **大文件批量编辑前先备份**。2026-10-24 曾把 `liltoon_material_factory.gd` 截断为 40 行，只能按调用点重建。
7. 只改项目内文件，不做破坏性操作。描述按 shader 路径进程内缓存，改完需重载插件才生效。

### 记录与上报

8. **差异不得静默丢弃**。近似实现的语义差异要写进 `DEVELOPMENT_PRINCIPLES.md` §9；转换器未转换/近似的项必须报给用户。
9. 阶段外临时插入的修复记入 `ROADMAP.md` 的 `SCOPE LOG`，注明影响阶段，不静默扩大当前阶段范围。
10. 每个阶段至少在 `docs/evidence/阶段N/` 留 1 张关键截图 + 1 段说明；未归档视为未完成。
11. 度量口径：`docs/参数对齐矩阵.md`（参数级）+ `docs/其他_161审计.md`（行为级），未对齐项数即进度指标。

### 环境硬限制（避免重复踩坑）

> 下表是**原开发机**（Intel UHD 617 / D3D12 / Win10 IoT）的实测边界。2026-10-29 已换机（RTX 4060 / Win11），

| AudioLink | 依赖音频总线与频谱全局 uniform | 放 P10，可选，不阻塞 |

| MCP 截图通道 | 编辑器长时运行后失效 | 重启编辑器再拍，或用直跑日志 |
| 渲染进程密集启动 | 2026-10-27 共四次 `0x139` (3)，均在短时间内连续起进程时发生；实测无冷却约 14–15 次后崩，段间静默几分钟则 21 次全过；内核池与空闲内存全程平稳，**不是泄漏** | **不要在短时间内频繁 run**：连续 5–10 次后静默几分钟再继续，不设固定节奏。用 `tools/check_all_shaders.ps1` 逐进程执行（别用 `Start-Process` 起后台，会被会话清理带断）；中断后用日志里的 `START` 行定位 |

## 四、上下文链接丢失：症状、原因、恢复

### 症状

- 会话只剩最近几轮，往上翻不到更早内容；
- 会话标题变成与内容无关的名字；
- "上文"在模型侧完全不存在，需要重新交代背景。

### 原因

对话正文与索引是**分开存储**的：

```
%LOCALAPPDATA%\CodeBuddyExtension\Data\<userId>\CodeBuddyIDE\<userId>\
  history\<workspaceHash>\<conversationId>\
    messages\<messageId>.json      ← 正文，一条一文件
    index.json                     ← 顺序表：哪些消息属于哪一轮
```

`index.json` 很小且频繁重写。进程被强杀、蓝屏或断电时，它可能被清成**全 0 字节但保留文件大小**（2026-10-27 14:48 的 `0x139` 蓝屏就造成了这个结果，172,199 字节全为 `0x00`）。客户端重启后发现索引损坏，会把它改名成 `index.json.corrupted.bak`，再**用残存内容重建一个残缺索引**——于是 UI 只能看到最近几轮，而 `messages/` 里的正文通常**一条都没少**。

### 诊断与恢复

```powershell
# 1) 体检：对比正文条数与索引覆盖（只读，不改文件）
python tools/rebuild_chat_index.py

# 2) 备份整个对话历史（建议定期做）
python tools/rebuild_chat_index.py --backup D:\CodeBuddyBackup

# 3) 修复：必须先完全退出 CodeBuddy，否则运行中的客户端会用内存索引覆盖回去
python tools/rebuild_chat_index.py --apply
```

`--apply` 会先把现有 `index.json` 备份成 `index.json.bak-<时间戳>`，再按 `messages/` 重建全部轮次结构，最后重新打开 CodeBuddy 即可加载。

**恢复边界**：

- 只损坏 `index.json` → 可 100% 恢复；
- 同时有少量 `messages/*.json` 被清零（崩溃瞬间正在写的那条）→ 该条无法恢复，其余完好；
- 恢复版索引**不含 `usage` 字段**（token 统计没落盘），表现为每轮 token 数显示为空，不影响消息加载。

### 预防

1. **重要结论当场落文档**，不依赖对话记忆。本文档 + `ROADMAP.md` + `SCOPE LOG` 才是长期记忆，对话只是临时载体。
2. 每次重要分界线后跑一次 `--backup`。
3. 长期无人值守跑任务前，先确认没有未保存的索引写入（干净退出一次 CodeBuddy 再启动）。
4. 若再次出现蓝屏，重启后**第一件事就是跑体检**，尽早发现、尽早重建。
5. 任何渲染类 run 都按最小负载执行（单 shader、关 MSAA 与阴影）；一旦蓝屏，**立即停手汇报，不要重试同一条命令**。

## 六、什么算"重要分界线"

满足任一条件才停下来找用户：

- 一个阶段做到验收全绿、准备进入下一阶段；
- 遇到 B 类功能，需要在"继续逼近"与"按性能妥协"之间做取舍；
- 出现与原版行为不一致、但无法自行判定的差异，需要用户裁定保留与否；
- 发现 `liltoon_gd` 的实现优于原版，需要用户决定是否保留；
- 遇到新的环境硬限制，导致原定方案必须降级；
- **gdmcp 的 9080 端口连不上，或 Godot 编辑器意外关闭**（此时可以直接停工汇报）；
- 需要用户在本机做无法自动化的操作（重启编辑器、手动烘焙、安装驱动）。

除此之外——继续做，不要问"继续"。
